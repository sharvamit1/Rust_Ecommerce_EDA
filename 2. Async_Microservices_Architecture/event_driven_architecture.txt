Asynchronous Event-Driven Architecture (EDA)

===========================================================================

In an Event-Driven setup

1. The Core Shift: The order_service completely stops making direct connections to the payment_service (port 8081 is removed from its code entirely). It no longer waits or cares if the payment service is up, down, fast, or slow.

2. The Shared Broker: We will introduce a lightweight, in-memory Event Broker inside workspace. When an order arrives, the order_service simply publishes an OrderCreated event to this broker and immediately returns a success message to the user.

3. The Consumers: The payment_service shifts from an HTTP/TCP listener to an active event subscriber. It continuously pulls or listens for OrderCreated events from the broker, processes them asynchronously, and publishes a PaymentProcessed event back.

===========================================================================

Set up this architecture

1. libs/event_broker: The multi-producer and multi-consumer broadcast channel using Tokio for services to pass events in memory.

2. Refactored order_service, payment_service: Updating them to pull from and push to the broker instead of dialing raw TCP ports directly.

::: Scenario payment failed for Order 1004 :::

1. The Ingestion: The order_service took the client request for item #101, quickly returned "Order accepted" to the client, and pushed the OrderCreated event to the broker.

2. The Distribution: The event_broker_service captured that event from the order service and instantly distributed it to all background workers.

3. The Asynchronous Rejection: The payment_service caught the event, saw (user_id: 999), evaluated the failure condition, printed Payment rejected due to insufficient funds, and pushed "payment failed" event back to the broker.

4. The Closed Loop: The event_broker_service broadcasted that payment failure event, and the order_service (which was listening in the background) caught it and printed received event (Payment FAILED for Order #1004)

::: Custom Broker vs Kafka Protocol :::

1. The Central Hub (TcpListener) - Instead of using Kafka’s protocol, we used Tokio to open a raw TCP server listening on port 8082. This port became our central message bus. Every microservice (order_service, payment_service, shipping_service) connects to this single port upon startup.

2. The Subscriber Registry (Arc<Mutex<Vec<...>>>) - Inside the event_broker_service code, we created a shared list protected by a thread-safe lock: Arc<Mutex<Vec<OwnedWriteHalf>>>. Whenever a service connects to port 8082, the broker splits the network socket and saves the writing half of that connection into this vector. This vector acts as a registry of active subscribers.

3. The Broadcast (Fan-Out) Mechanism - When the order_service pushes an OrderCreated event into port 8082, the broker catches it. It then runs a for loop over that registry vector, duplicating the JSON bytes and shoving them down every open connection stream. This is how the payment_service and shipping_service receive the event simultaneously without ever talking to the order service or to each other.
